# NeoForge → Fabric 自动移植闭环

适用前提：主代理和子代理模型默认都具备直接读图能力；不具备则拒绝执行本 skill，不提供无视觉降级流程。

把原实现的行为迁到目标平台，而不是把编译错误消掉。以**上游源码、原版运行结果、目标端状态和真实画面**共同验收。mdb 是观察与操作游戏的工具，不是加载器兼容层，也不会替你实现移植。

## 0. 强模型规划与审查，弱模型执行

**本 skill 默认由强模型主代理读取并主持移植，典型实现是子代理机制：主代理写 roadmap 与审查意见，较弱/低成本模型的子代理作为 worker 干活。** 不把整个模组和一句“移植完成”直接扔给 worker，也不让主代理只转述 worker 的成功报告。

| 角色 | 负责 | 不得代替 |
|---|---|---|
| 主代理（强模型） | 读源码定边界、编写/更新 roadmap、决定平台语义与允许差异、派发任务、审查真实 diff 和证据、裁决与验收 | 不把架构决策、验收标准或最终通过权下放给 worker |
| worker（弱模型） | 按任务单查指定源码、实现适配、编译、用 mdb 操作游戏/截图/读回、复现缺陷、按审查意见修正 | 不自行扩大范围、删除行为、降低门禁、接受新基线或宣称整个移植完成 |

主流程：**主代理调研 → roadmap → 有界任务单 → worker 实现与 mdb 闭环 → 主代理审查 → worker 返工 → 主代理复审/集成验证 → 更新 roadmap**。第 1–3 节主要由主代理负责；第 4–5 节由 worker 在授权范围内执行；第 6 节最终裁决属于主代理。主代理可执行只读探测和关键复现，不必重复 worker 的全部机械操作。

- roadmap 按可验收的纵向行为切片，写清依赖、owner、不变量、验收和非目标；弱模型需要更明确的契约，不需要被拆成彼此断开的叶子文件任务。
- 实施跨度过大时，保留纵向验收契约，按单一 owner 的定义—接线—调用方闭包派发；本轮完成条件与最终切片通过条件分开写，见 delegation 参考文档。
- 每次派发携带仓库约束、精确源码路径、允许修改范围和证据要求。子代理不一定继承父会话的指令或上下文，不能只说“按前文做”。
- 主代理亲自读实际 diff、相关上游源码和关键日志；涉及画面时亲自打开关键截图。worker 的自评、退出码和 PNG 文件存在都不能替代审查。
- 架构/语义不确定、越界依赖或连续失败无新证据时，worker 带最小复现升级给主代理；主代理缩小任务、补查源码或重定路线，不靠反复换 worker 碰运气。
- 默认一个可写 worker；仅对真正独立的行为切片并行，且隔离 worktree、构建输出、session、gameDir 与存档。共享注册/网络/构建接线由主代理指定唯一写入者，集成后重新验证。
- 按用户指定型号调用宿主派发接口，记录参数、结果和实际模型元数据；缺少解析信息时如实注明，无需模型自述。确实不能派发或选型时报告限制，仅按已有授权降级；串行保留规划→执行→审查，不冒充独立审查。遵守仓库对子代理写入的限制。

开始派发前读 [references/delegation.md](references/delegation.md)，其中包含 roadmap、worker 任务单、审查意见及交接模板。

## 1. 先建立工作契约

读目标仓库的开发约束与现有移植记录，确定并记下：

- 上游源码路径、版本/commit、许可证；目标仓库、分支和允许修改的目录。
- 依赖链：目标模组依赖的、同样需要移植的库，先读基线声明的依赖版本，按基线实际编译所对的版本/分支取源，库与模组的固定版本成对记录；换基线时整套更换，不拿别的版本线的库顶替。
- 精确 Minecraft 小版本、JDK、映射、加载器和 API 版本。默认保持同一 MC 小版本，避免把版本升级和加载器迁移混成一项工作。
- 已移植范围、这轮要接通的用户行为、非目标、允许的平台差异和验收证据。
- 实际构建任务、源码集、资源生成方式、运行目录、测试存档与显示环境。

mdb 已验证的双加载器环境是 **Minecraft 1.21.1 / NeoForge 21.1.x / Fabric**；其他 1.21.x 小版本先核实工具及依赖支持，不把 1.21.1 的成功外推为全系列兼容。

缺少影响路线的输入时先澄清；不把未授权的功能删减、依赖替换或数据迁移当成默认决定。源码和生产数据分离：只在隔离开发环境操作，参考源码保持只读，原始存档先离线复制。不部署、不推送、不修改真实玩家世界。

维护一份简短的移植记录，至少包含：

```text
行为 | 上游 owner/调用链 | 平台差异 | 目标实现 | 验收方法 | 状态/证据
```

状态区分：未接入、可编译、可启动、行为已验证、发布物已验证。不得用“可编译”替代“移植完成”。

### 环境准备：先建立两端参考源码树

在开始适配前，按 [references/source-workspace.md](references/source-workspace.md) 准备源/目标端 API 与 Minecraft 源码。不能只约定“遇到问题查源码”：先核实已有树，缺失时用对应工具链生成 MC sources、获取精确版本 API sources，并提取到目标工程旁的 `../port-reference/` 等独立参考目录（仍在授权工作根内）。记录路径、版本、映射、生成方式与访问放宽，透传给 worker；这些源码只读、不进入构建依赖或提交。

## 2. 源码驱动选路，不机械替换 import

在相关源码目录内用 rg/fd 定位真实行为 owner、直接前置和立即调用方；不扫描整台机器，不无限追逐类型引用。涉及 MC/API 签名和注入行为时查本地对应版本源码，不靠记忆猜方法。

按以下顺序寻找目标实现：

1. 原有领域代码能否原样保留。
2. vanilla 是否已有等价能力。
3. Fabric API 是否提供对应事件、注册、网络或存储接口。
4. 对照 NeoForge patched Minecraft 与目标 MC 源码，确定上游是否依赖了注入的方法或生命周期钩子。
5. 没有等价能力时，围绕真实 owner 写最小平台 adapter；必要的 mixin 说明注入位置、时序及运行验证方式。

参考兼容项目只能提供线索，不默认成为依赖；采用代码必须记录来源和许可证。反编译源码可能已应用 access transformer/widener，不能把放宽后的可见性当成 vanilla 契约。

**保持不变量：**

- 默认保留包名、类结构、继承/组合关系、算法与公共行为，只改必要的平台边界。
- 保留注册 ID、领域单位、配方、NBT/组件、配置和存档语义；网络编码或对外 API 的差异必须明确记录，不能默认两种加载器可互联。
- 不伪造 `net.neoforged.*`，不为一个功能建立第二套领域框架，不实现无边界的通用转换层。
- 不用 no-op、恒定返回、吞异常、关闭必要 mixin、剔除必要源码或删除功能换取假绿。

高风险平台语义按 [references/verification.md](references/verification.md) 检查。遇到 capability/transaction、线程、同步、保存问题，先写清语义再改代码。

## 3. 按用户行为纵向交付

选择一个可以实际操作并验收的行为，把它的注册 → 状态 → 逻辑 → 网络/menu → 渲染/交互接通；没有 UI 的功能不强造 UI。包括真正必要的前置和调用方，但不因一个常量引用扩展整个模块。

优先顺序：

1. 建立最小可靠构建与启动基线，先解决入口点、资源和注册生命周期。
2. 接通一个代表性端到端行为，暴露真实平台差异。
3. 将已验证的适配方式复用于同类功能，再处理差异分支。
4. 持久化、卸载/重载、多人同步与发布物检查放到对应里程碑，不无限延后。

只做平台清点而不接 owner、连续修叶子而游戏始终无法验证，都应重估切片边界。

## 4. 用 mdb 建立可控的真实游戏环境

加载可用的 mdb 操作 skill，并读本机 `mdb --help` 及相关子命令 `--help`。参数以实际版本为准，不猜 RPC 字段。没有 native `mdb` 时用同版本 CLI jar，后文 `mdb` 代表选定的命令。

- CLI 与游戏中的调试工具版本匹配。通过 `mdb jar --loader fabric|neoforge --output <gameDir>/mods` 安装对应工具 jar；首次启动前按 jar 元数据补齐语言适配器与加载器依赖，避免重复版本。
- 工具 jar 放在**被移植项目/参考消费者项目**的 `mods/`，不放到调试工具自己的 dev classpath 注入目录；不进入目标模组的发布依赖。
- 目标端与参考端使用不同 session、gameDir、存档副本和端点；资源不足时顺序运行。不让两个进程打开同一存档。
- 隔离运行须显式指定本轮 `--sessions-dir`；registry 和启动日志不属于 gameDir，省略它会写默认用户目录。start、路由命令和 stop 使用同一 registry（或同一 `MCDEBUG_SESSIONS_DIR` 环境）。
- 客户端统一用 `mdb session start` 启动 owned session，结束用 `session stop`；不手写裸客户端启动器，不按进程名批量杀 Java/Gradle。
- session 后端需要可用的 Gradle wrapper 和 `runClient`。NeoForge 的启动参数交给 session 适配，不手工用 `--args` 覆盖其启动参数文件。
- 截图需要真实客户端、可用显示服务和 GL；只有专用服务器拿不到像素。无显示环境时记录阻塞，不用数据 JSON 冒充视觉验收。
- 启动前显式选择并验证显示（如 `glxinfo -B` 看渲染器与 direct rendering），优先硬件加速；代理 shell 继承的 `DISPLAY` 可能不可用。软件渲染得到的截图不能充当视觉基线，证据里记录所用显示。
- **截图前关闭原版遮挡提示**：每个测试 gameDir 启动前将 `options.txt` 的 `tutorialStep` 设为 `none`，避免新世界的 WASD/鼠标教程；已启动时用客户端原生 `Minecraft.getInstance().getTutorial().setStep(TutorialSteps.NONE)` 立即关闭并保存。每次连接本地离线测试服后，用客户端原生 `SystemToast.forceHide(Minecraft.getInstance().getToasts(), SystemToast.SystemToastId.UNSECURE_SERVER_WARNING)` 定点关闭“不安全聊天 / original message”提示。通过 mdb 客户端反射调用即可；`demand`/`gui-only` 下不要靠等待其自动消失。随后强制新帧并读图确认 GUI 无遮挡，不通过裁图、隐藏整个 HUD 或修改发布模组来掩盖这些测试环境提示。

- **新区块的世界截图需要地形渲染预热**：传送或首次加载区块后，`demand` 下少量截图帧可能只画出天空、粒子或实体，地形网格仍在编译/上传；不能据此判定方块模型缺失，也不能把服务端生成计数当视觉通过。必要时临时恢复连续正常渲染，确认客户端区块已收到、网格队列完成并读图看到实际地形，再采证；结束恢复原渲染策略。GUI 截图与世界地形截图分别核实。

以下路径、任务、存档名是占位符，须按目标项目替换：

```bash
mdb --sessions-dir /abs/experiment/sessions session start port-target --project /abs/target --task :module:runClient \
  --game-dir /abs/target-game --world TestWorld --render demand \
  --width 1280 --height 720 --wait-seconds 180
mdb --sessions-dir /abs/experiment/sessions --session port-target status
mdb --sessions-dir /abs/experiment/sessions --session port-target gui status --brief
```

`--world` 指已有 `saves/` 子目录名，不是显示名。没有测试世界时先进入标题页，通过游戏 UI 创建隔离世界；不伪造存档或删除锁。确认 `world_ready`、`inWorld`、实际加载的版本/jarPath 和窗口尺寸，socket 文件存在不算就绪。

需要原版行为对照时，用同样方式为原源码或独立参考消费者建立 NeoForge 会话。只有参考服务端时只能证明服务端行为；拿不到原版画面时明确标记视觉基线缺失。

**原版端默认不可信。** 参考实现若是第三方或自动化产物，先过三道门才可作行为基线：客户端启动到主菜单且 0 ERROR；进入世界且 0 ERROR；跑满一段 tick 且配方/标签/网络等同步正常。缺陷逐个作为针对固定提交的编号补丁保存，并写明目标端移植要如何处理同一处代码。缺陷持续增长而无收敛时，停止修补，带证据上报并重选基线或改用能正常运行的官方版本做行为对照，不要悄悄变成基线的维护者。

`--session NAME` 自动选择服务端/客户端平面。显式连接时，服务端用 `--socket`/`--tcp`，客户端用 `--client-socket`/`--client-tcp`；不能拿服务端 socket 请求截图。独立多人服不冒充 session 的集成服务器。

后续示例省略重复的 registry 参数，实际调用仍须沿用本轮设置。准备发布物验证时读 [references/production-consumer.md](references/production-consumer.md)，选择受 session 管理的生产启动方式；默认 Loom runClient 不是生产环境。

## 5. 必须执行的反馈闭环

每轮选一个可证伪假设，例如“客户端显示停滞是同步丢失，而非服务端逻辑未运行”。按下列顺序推进：

### A. 准备可复现夹具

- 从源码确认注册 ID、配方条件、槽位、字段、侧面规则和所需资源，不猜数字。
- 在固定测试区域准备地板、方块、输入、能源/流体及玩家位置，确保区块加载、玩家可达。
- 用 `world.*`、`inv.*`、`storage.*`、`be.*` 快速布置；读回确认。通用库存 API 不支持的自定义容器，走其真实存储接口或 GUI，不据此认定实现有错。
- NBT/反射可建立初始状态或定位问题，但**不能把预期输出直接写进去再宣称行为通过**。它们可能绕过放置、权限、同步和保存逻辑，最终验收要覆盖实际用户路径。
- 两端夹具表达同一领域状态，不要求原始 JSON/底层单位完全一致。

### B. 修改与最小构建

只修改当前假设涉及的行为边界。按项目规定跑受影响的编译/现有 focused tests；语义转换适合补小型确定性回归，但不要为一个修复建立新测试框架。编译失败先读首个根因，而不是堆补丁绕开报错。

### C. 确认新代码实际生效

| 变更 | 快速迭代方式 | 最终验证 |
|---|---|---|
| 已加载类的方法体 | 编译正确源码集，再 `gui hotswap --classes <绝对输出目录>` | 正常重启重放行为 |
| 当前 Screen 类的结构 | 可尝试 `gui reload-screen --classes <目录>` | 正常重开/重启，排除副本效果 |
| 贴图、语言、模型 | `gui reload-resources` | 检查实际新帧与资源日志 |
| 注册、网络、mixin、初始化、其他结构或依赖 | 停止并重启 owned session | 核对新版本与实例 |

hotswap 不重跑已有对象的构造器；reload-screen 不等于全模组热重载。检查返回的失败/结构差异与实际更新数，`changed:0` 不算生效。换发布 jar 必须重启；不能一边改源码一边继续操作旧 jar 的进程。

### D. 操作游戏并读取权威状态

触发真实放置、使用、输入或 GUI 操作；读取服务端方块、库存、存储及 NBT 验证结果。等待统一用有界 `wait.until`；先读谓词引用的字段，再短等，避免在错误字段上空耗长超时。

长耗时 tick 逻辑可使用 `wait until ... --sprint`，仍由原版引擎推进；不要新增 `tick.run` 一类 RPC。单 BE 的 `be.tick` 不会推进邻居/世界，不能拿它证明网络、传输或完整世界行为。墙钟逻辑不能靠 sprint 验证，手动修改 tick rate 后恢复原值。

### E. 看真实界面，而不仅是拿到一张图片

服务端写入后先 settle，然后查看 Screen 结构与截图：

```bash
mdb --session port-target gui settle
mdb --session port-target gui open-block --x 100 --y 64 --z 100
mdb --session port-target gui screen --brief
mdb --session port-target gui screenshot --mode gui --annotate --draw-log \
  --out /abs/evidence/iteration-01.png
mdb --session port-target gui problems --brief
```

此示例要求相应位置已放置可打开的方块、玩家在可达范围内。容器用 `--mode gui`，其他 Screen/世界画面用 `--mode window`。

**必须使用 agent 的读图能力打开返回的 PNG**，检查布局、文字、材质、进度、槽位、高亮与裁剪。生成 PNG 或看到 hash 变化，不等于已经检查画面。记录截图路径和实际观察，不凭预期描述图片。worker 自行读图并记录观察，主代理审查时独立复核关键截图。

从 `gui screen`/标注图取得当前槽位或控件 index，再 `gui click --slot N|--widget N|--text ... --shot gui --screen`；hover 看真实 tooltip，必要时 scroll/key/type/drag。不要复用旧 Screen 的控件编号或上一次窗口尺寸的像素坐标。

客户端推荐 `demand`，尤其无窗口焦点的环境；验证世界渲染不能以跳过世界的 `gui-only` 替代。截图、draw log、menu 数据与服务端状态交叉核对：

- 服务端正确、menu 错误：查网络包、同步时序、菜单数据与线程。
- menu 正确、画面错误：查客户端状态、绘制坐标、资源、裁剪与渲染层。
- 点击无效：先查玩家距离、槽位规则、手持物、目标控件与动作结果，再查实现。
- 工具名称或帮助概述似乎不支持所需动作时，先核实其实际调用路径和默认参数，再判断能力缺失；复合工具的后续视图失败不证明前面的世界交互未发生，需读回权威状态。
- 渲染异常：先查 `gui problems` 和 `<gameDir>/logs/latest.log`，不能把 guard 保住进程当成成功。

`screen.*` 只是服务端假玩家菜单，没有像素；客户端 BE 也不一定同步库存。权威库存读服务端，客户端显示读当前 menu，不互相替代。

### F. 差分、修正、重放

保存原始 RPC 返回、截图、相关日志和版本身份，对照上游源码/参考端结果。先分类为夹具问题、工具限制、预期加载器差异或移植缺陷，再改真实 owner。

每次修正后重置夹具并重放同一操作；成功后加一个相关边界检查，不能以“这一帧看起来正常”结束。连续两轮同一失败且没有新证据时，停止盲目改动，缩小复现或补观测点。

## 6. 验收与结束

具体验收表见 [references/verification.md](references/verification.md)。存在可信的行为基线时，按 [references/behavior-oracle.md](references/behavior-oracle.md) 在两台服务器上自动生成大规模对照场景（分层顺序、场景生成、规范化、差异分诊、测试设施陷阱、并行提速）。按当前切片风险选择，涉及的行为必须有证据；未跑项明确写“未验证”，不伪装为通过。可选执行其中的“NeoForge 存档 → Fabric 加载”互操作测试，同时验证服务端状态与截图中的机器表现。

完成至少意味着：

- 行为 owner 已接通，没有依赖占位实现；规定的构建和回归通过。
- 游戏实际运行了新代码，真实操作后的服务端状态符合预期。
- 涉及 GUI/渲染时，已读图并验证交互，未新增相关渲染故障。
- 正常重启后可重现成功，不依赖热加载副本或反射强制状态。
- 里程碑的发布 jar 在独立干净消费者环境验证，而非仅靠自身 dev classpath。Gradle consumer 可用来验证 jar 加载，但其开发重映射结果不能冒充未经重映射的生产客户端证据。

worker 交付只进入“待审查”，主代理按真实 diff 和原始证据给出通过、需修改或阻塞结论；返工后检查修复及相关回归，集成后再更新 roadmap 为已验收。审查不能仅重复 worker 的摘要，也不因排期压力放宽行为契约。

报告只列：改动边界、已验证行为与证据路径、允许差异、未验证风险、下一步。不要把单切片成功宣称为整个模组移植完成。

结束或阻塞时，保存日志与失败夹具，正常停止自己启动的 owned sessions，核对状态及对应进程退出；附加会话不停止，锁文件不手删，共享 Gradle daemon 不清杀。长期记录保留当前 commit、最后一轮结果与下一条可执行动作。

若版本不支持、缺少依赖/显示环境、无法取得必要基线，或修复将超出授权边界：停止相关分支并给出**证据、已尝试路径、具体阻塞和所需输入**；可继续互不依赖的已授权切片，不用降低验收标准换取完成。
