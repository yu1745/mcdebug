# 行为预言机：大规模自动生成的对照测试

用途：当存在一个可信的行为基线（原加载器、旧版本或上游官方版）时，在两台同时运行的服务器上，用同一份数据自动
生成成千上万个场景，逐场景比较结构化结果，把"移植后行为是否一致"变成可重复、可量化的证据。它找到的是编译通过、
能进世界、手测也难发现的缺陷：能力名拼错导致整类工具失效、伤害阶段挂错事件、平台查找时机不对导致掉落丢失、
约定标签为空、事务里丢了变更通知。

前提：基线已通过 SKILL.md §4 的三道门（启动、进世界、tick 健康），并且锁定到它真实的上游 commit（数据用 blob
哈希定位，见 1.20→1.21 陷阱 §7）。基线不可信时，差异无法归因。

## 1. 分层顺序

由内向外，每层只在前一层基本一致后再做；外层的差异要先排除内层原因。

| 层 | 场景来源 | 比较什么 |
|---|---|---|
| 数据 | 两边加载后的配方、标签、注册表、数据文件 | 规范化后的结构；条件配方要穷举所有真值组合 |
| 组装/属性 | 每个工具 × 每个部件槽 × 每种材料；每个修饰符 × 等级 | 生成物的完整数据（属性、修饰符列表、耐久） |
| 挖掘 | 工具 × 头部材料 × 方块（放在固定立方体中心） | 是否破坏、剩余方块数（范围工具）、掉落、工具耗损 |
| 近战/远程/护甲 | 工具或护甲 × 材料/修饰符；固定的攻击者或目标 | 目标掉血、旁边目标（横扫）、效果/着火、投射物属性、耐久 |
| 右键交互 | 能力工具 × 方块层 × 普通/潜行 | 方块结果、作用范围、耗损、掉落 |
| 容器/GUI | 菜单驱动：真实点击放入、Shift 取出 | 产物数据、消耗的输入、产物是否进入背包 |
| 机器 | 方块实体 + 燃料/输入，显式推进 tick | 输出种类与数量、剩余、燃料、拆除时的掉落 |

一层通常是一个独立脚本，输出 `rows`（全部场景）和 `diff`（不一致的），中间结果按工具或类别落盘，便于只比较不重跑。

## 2. 场景生成

- **从数据枚举，不手写列表**：遍历工具定义、材料、修饰符、配方目录。手写列表只用于"代表性"维度（如几种方块、几种
  头部材料）。
- **先在基线上探测合法性**：先在基线上确定每个槽位可用的材料、哪个代表性工具能接受某配方，再在两边跑相同场景。
  基线拒绝的组合记为 `skipped`，不计入比较。
- **只对两边都存在的东西比较**：先分别探测两边已注册的 id（物品、修饰符），只取交集；一边独有的单独列出。
- **标签解析**：配方里的标签要落到具体物品才能放进容器。先查双方的标签数据，再按约定命名推断（`c:ingots/x` →
  `x_ingot` 等），解析不到就跳过并计数。跳过数异常高时，单独检查是否跳过了原版或本模组的物品。
- **批处理**：大量同类构建（组装物品）写成一个 datapack 函数，一次执行、一次扫描读回，而不是每个场景一次 RPC。

## 3. 规范化与比较

- 去掉默认值（如 `broken: 0`），浮点舍入到固定位数，保留有语义的列表顺序（修饰符优先级）。
- 新旧格式统一：1.20 NBT 键与 1.21 组件/custom_data 键、`FluidName/Amount` 与 `id/amount`。
- 单位统一：Fabric 流体 droplet（81/mb）与 mb；读运行时报告的单位，不要写死。
- 有随机成分的量（箭速、扩散）用容差比较，并检查差值的均值与标准差：无偏的小噪声可以接受，系统性偏移就是差异。
- 结果字段要覆盖"副作用"：掉落物、拆除后掉落、残留在容器里的东西。很多缺陷只体现在副作用上。

## 4. 差异分诊

对每类差异依次判断：

1. **测试设施问题**（最常见，先查）：见第 5 节。特征是差异随运行顺序、并发度或时间变化。
2. **概率性**：概率触发的修饰符、耐久减免。两个方向都有、没有系统偏向；用逐次立即读取的方式重测，比较触发率和
   持续时间分布，而不是单次结果。
3. **确定性**：串行重跑仍稳定复现。再区分：
   - 原版版本差异（同一机制在新版本原版里变了，官方新版也会如此）——记录，不修；
   - 上游有意修正（新版本本身修过）——记录，不修；
   - 基线缺陷（第三方基线自带）——编号记录，在平台副本里修；
   - 移植缺陷——编号记录，修。
   修复后重跑整层，确认差异消失且没有引入新差异。

## 5. 测试设施陷阱（每条都实际出现过）

- **fake player 不 tick**：它没有网络连接，不会运行 `Player.tick`，所以物品冷却、着火、状态效果永远不会过期，会
  泄漏到之后所有场景（例如某修饰符设了冷却后，后面所有使用都 PASS，两边"一致"其实是都没执行）。每次动作前重置
  这些瞬态状态；用"两边都没产生结果"的计数做健全性检查。
- **反射成员名随映射变化**：fake player 依赖的私有字段/方法在 intermediary、Mojang、SRG 下名字不同，旧版回移植尤其
  容易漏。找不到时要报错，不能静默跳过（静默会让动作"成功"但没有效果）。
- **调用名翻译错误**：Yarn 与 Mojang 同名方法语义可能不同（如"停止使用"与"释放使用"）；回移植时逐个核对。
- **显式推进 tick 时传旧状态**：手动驱动方块实体 ticker 时，每 tick 都要传当前方块状态；方块实体会改自己的状态
  （点燃、多方块的"在结构中"标记），传开始时的状态会让后续 tick 看不到变化。
- **世界 tick 与手动 tick 不同**：结构检测、燃料查找、掉落物生成可能依赖真实世界 tick 或游戏时间；手动 tick 不推进
  这些。等待条件成立（轮询状态），不要假设 N 次手动 tick 就够。
- **fake player 背包里有无关物品**：一些成就奖励（如首次 tick 发的指南书）会不定时进入 fake player 背包，两边时机不同。
  比较"这次操作让背包新增了什么"（操作前后求差），不要比较整个背包。
- **场景间残留**：掉落物、下落方块、未熔化的物品、上一场景的实体都会被下一场景吸收或计入。每个场景前清理自己区域，
  拆除后再收集一次。
- **被杀的生物留下经验球和掉落物**：批量 `kill` 测试生物后，经验球每 tick 互相查找合并，累积上万个后服务器被 watchdog
  杀掉（崩溃栈在实体区段遍历里）。清理生物时一并清掉经验球与掉落物；崩溃后存档里还留着它们，重启后先清。
- **环境不一致**：生物群系（温度类特性）、时间（亡灵在白天着火）、区块加载状态。给每个场景统一设置。
- **命令失败的措辞因版本而异**：对"已经是目标方块"等无害失败，按两边各自的措辞忽略，其余错误必须抛出。
- **工具链重建覆盖了部署物**：重建发布消费者时可能用旧的调试 mod 覆盖新的；部署后先确认服务端提供了新方法。
- **构建失败被输出过滤掉**：只 grep 部分输出时，编译失败可能看起来像成功；检查产物时间戳或内容，再部署。
- **白名单构建**：新增平台源码要同时加入构建白名单，否则不会编译。

## 6. 并行与速度

- 两台服务器同时跑，每个场景在两边同时执行。
- 每台服务器开多个 worker，每个 worker 独占一块世界区域（cell），场景从队列取；RPC 往返（进程启动）才是瓶颈，
  服务器本身多半空闲。8 个 worker 通常能把一层从十几分钟压到一两分钟。
- 调试客户端用原生编译（如 GraalVM native-image），单次调用从数百毫秒降到十几毫秒。
- 并行结果中不一致的场景，**串行重跑**一到两次；只有串行仍复现的才算差异（并行时世界 tick 与 RPC 交错，依赖
  tick 时机的行为可能仅因时机不同而不同）。
- 按坐标分批：一批场景摆在网格上，只等一次 tick、只扫描一次。
- 不在每个场景结束时清空整个背包之类的全量操作；只清实际用过的东西。

## 7. 产出与记录

- 每层在验收文档里写一段：场景来源、规模、耗时、一致数、剩余差异的分类与理由、未覆盖的部分。
- 每个修复的缺陷在基线/缺陷文档里编号：现象、根因、如何发现（哪一层、哪个场景）、修法、修后测量。
- 测试设施的修复（调试工具本身的 bug）单独提交到工具仓库，并在工具文档里写明新的语义。
