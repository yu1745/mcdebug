# B4 报告 — managed session 工作流
实例: CLI 自己起的客户端（项目 `/tmp/neo-verify/session-target`，NeoForge/ModDevGradle 消费者项目，mods: `mcdebug-neoforge-0.7.0.jar` + KotlinForForge 5.12.0）
- 服务端平面: `/tmp/neo-verify/session-target/run/mcdebug/socket`（发现文件 `mcdebug/port`）
- 客户端平面: `/tmp/neo-verify/session-target/run/mcdebug/clientSocket`（发现文件 `mcdebug/clientPort`）
- registry: `MCDEBUG_SESSIONS_DIR=/tmp/neo-verify/agent-b4/sessions`；display `:90`；存档 `NeoWorld`

CLI: `java -jar /tmp/neo-verify/cli/mcdebug-cli.jar`，`--version` → `mcdebug version 0.7.0`

## 失败项（原样）

无任务级 FAIL。以下为按任务包字面执行时记录到的两条非一致性命令（F1 立即可绕过，F2 是预期边界）：

### F1 `session logs --tail`（任务包措辞）
命令: `mcdebug session logs b4-menu --tail 5`
响应: `Usage: mcdebug session logs [<options>] <name>` + `Error: no such option --tail`，exit 1
期望: TASKS.md 写 `session logs --tail`；CLI 帮助实际选项是 `--lines=<int>`（`session logs --help` 明确写出）
影响: 可绕过 — 用 `session logs <name> --lines N`（本报告任务 4 即如此）。属于任务包与帮助的措辞差，不是工具缺陷

### F2 主菜单会话上调服务端平面（预期边界，非缺陷）
命令: `mcdebug --session b4-menu status`（b4-menu = 无 world、停在 TitleScreen 的会话）
响应: `error: session has no integrated server endpoint (not in a singleplayer world)`，exit 1
期望: 任务 3 的"两平面都成功"只可能在进世界后成立；`session status --help` 也写了 "client readiness is not world readiness"
影响: 无阻塞 — 先 `--world` 起会话（任务 2）再测路由即全绿。此时 `gui status`/`gui screenshot` 在主菜单会话上仍成功（TitleScreen 854x480 截图正常）

## 帮助/skill 缺口

1. **`MCDEBUG_SESSIONS_DIR` 环境变量未在任何帮助/skill 里出现**：TARGET 要求用它固定 registry，实测有效（`registry.lock` 与记录都落在该目录），但 root `--help` 只写 `--sessions-dir=<path>`，skill 也只说 `--sessions-dir`。只看文档的 agent 不知道有这个环境变量。
2. **`session start` 的 `--render` 默认值未写**：帮助列出 `--render=(continuous|demand|gui-only)` 但没写默认；我没传该参数，记录里却是 `render:"demand"`。skill/AGENTS 语境里全局默认是 continuous，managed session 悄悄用 demand，读帮助推不出来。
3. **`--batch` 与重复 `-c` 的区别观察不到**：帮助把 `--batch` 描述成"逐条打印状态、失败即停"的模式，暗示不带 `--batch` 的 `-c` 行为不同；实测不带 `--batch` 的两条 `-c` 同样打印 `[1/2]` 状态、同样在第一条失败时停止（stderr 也写 "(stopping batch)"）并返回失败码 3。要么文档过度区分，要么 `--batch` 已冗余——从外部无法判定。
4. **`session stop` 返回后 gradle wrapper 还会存活几秒**：stop 在 ~4 s 内返回 `state=stopped` 且 MC pid 已消失，但 wrapper（gradle-wrapper.jar runClient …）仍活着，~10 s 内自行退出。帮助/skill 没提这个窗口；立刻做"无残留进程"检查会误报，立刻重启同 gameDir 也可能撞上。
5. **`--socket` 对 `gui.*` 静默无效**：`--socket <路径> gui status` 不报"选项冲突"，而是忽略它走客户端发现（我在源码仓库目录下误触发了 CWD 相对发现，错误信息指向了那个目录的 run/mcdebug）。root help 确实另列了 `--client-socket`，但"传错平面选项会被静默忽略 + 客户端发现按 CWD 解析"这一交互要从失败中才能学到。
6. **session `state` 取值没有枚举**：实测见到 `client_ready / world_ready / stopped`，`session remove --help` 又暗示有 `failed / dead`。帮助/skill 均未列出完整状态机与各状态的含义，轮询/脚本化时只能猜。
7. 小项：skill 说 stop 后"port、clientPort、locks 会留下"，实测还会留下 `session-stop.json` 与 `client.json`（未提及，无害）；`--session` 与显式 transport 互斥有明确报错（`Error: --session cannot be combined with --socket/--tcp/…`，exit 1），这点文档写清楚了。

## 未能判定

- `--batch` 与重复 `-c` 是否在任何路径上有行为差异（例如输出格式或连接复用细节）——需维护者看源码。
- `session start` 在冷 Gradle（首次下载依赖/assets）下的耗时与 `--wait-seconds 300` 是否够用——本轮都是 warm 缓存（28–31 s）。
- `state=failed/dead` 的实际样子与 `lastError` 内容——本轮没有出现启动失败；未故意制造崩溃（会违反"失败不要修/不折腾实例"的边界）。
- wrapper 停止窗口的确切上界（观察到 ≤10 s；只采样了两次）。
