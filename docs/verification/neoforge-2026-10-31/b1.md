## 失败项（原样）
无整任务失败。以下为任务内观察到的非预期响应，均未阻塞任务（可绕过，绕法附后）：

### F1 raw craft.craft 传字符串 grid → -32603 内部错误（而非 -32602）
命令: `raw craft.craft '{"grid":["minecraft:oak_log",null,null,null,null,null,null,null,null]}'`
响应: `error [-32603] IllegalStateException: Not a JSON object: "minecraft:oak_log" data={exception:java.lang.IllegalStateException, at:[…CraftingOps.parseGridWith(CraftingOps.kt:206)…]}`
期望: 参数形状错误应报 -32602（点名参数）；帮助里没有任何 raw grid 的 JSON schema。
影响: 可绕过（grid 槽写成 `{"item":…,"count":…}` 对象即可）。

### F2 reflect get 读大集合静默截断
命令: `reflect get --class net.minecraft.core.registries.BuiltInRegistries --path BLOCK.keySet`
响应: `value` 数组 201 个 key；同路径 `BLOCK.size` → `1060`。无 `truncated` 标记、无任何提示。
影响: 可绕过（不能据此断言"某 modid 没有注册方块"）；黑盒下容易得出错误结论。

### F3 `reflect set --path`（不带 --field）被 CLI 拒绝
命令: `reflect set --root level --dim overworld --path rainLevel --value 0.75`
响应: `Usage: mcdebug reflect set… Error: missing option --field`（exit 1）
期望: 与 `reflect get --path` 一致地接受纯 --path；帮助未标注 --field 必填。
影响: 可绕过（--field 单独用即成功）。

## 帮助/skill 缺口（按重要性排序）

1. **G1 fluid 子命令帮助的单位是错的（对 NeoForge 有害）**：`fluid insert/extract --help` 写死 "amount unit is DROPLETS (81000 = 1 bucket)"、"extraction works in WHOLE-BOTTLE units (27000)"。本实例 `fluidUnit=mb`（1000=1 桶），27000 这个量子在 mB 下毫无意义——实测 `extract 333` 得 0。只有 `status` 的 `fluidUnit` 字段和 skill 提到单位随 loader 变化；子命令帮助从不提。传错数量级（81000）会得到看似合理实则错误的结果。
2. **G2 chunk 加载矩阵没人讲全**：`fill-box/clear-box` 在未加载 chunk 上 `-32008`；帮助说 get-region 会 auto-load，但**读完不持久**——紧跟着的 fill-box 仍然 -32008（实测）。真正可行路径是另一个组的 `world forceload --cx/--cz`，fill-box 帮助里没有任何指向。replace-box 同样受影响。
3. **G3 0 玩家服务器的实体寿命 + spawn 不贴地**：本实例无玩家，刷出的生物 ~3 秒内消失——`PersistenceRequired:1b` 也一样，vanilla `/summon` 同样消失（对照实验），且 `entity spawn` 不吸附地面（猪从 y120 掉到 y111，扫描框跟着落空）。find-entities 本身没坏，但帮助/skill 完全没提这两点，表现极像"scan 坏了"。建议 skill 写明：专用服测试实体要么用 `-c` 批处理秒级完成、要么先垫地板。
4. **G4 `inv.setSlot --nbt` 的落点语义未文档化**：NeoForge 实测整个 nbt 被原样塞进 `components."minecraft:custom_data"`，`{"components":{"minecraft:custom_name":…}}` 并**不会**产生真实的 custom_name 组件；而 `inv.getSlot` 原样回显你写入的 JSON，形成"成功了"的假象（`be.getNbt` 才揭示真相）。帮助只有一行 `--nbt=<text>`。
5. **G5 `storage get` 的 supportsInsertion/Extraction 自相矛盾**：满水锅报 `supportsInsertion:false`，但 `storage.transfer` 成功向空锅注入 1000mB（空锅也报 insertion:true/extraction:false——纯按当前状态推导）。skill 有一句"derived approximations"，`storage --help`/`fluid --help` 没有；按这个标志写断言必翻车。
6. **G6 reflect 帮助与 NeoForge 现实冲突**：组帮助两处写 "Mojang and intermediary names both work"、"--class (Mojang, intermediary or mod name)"，但 NeoForge 只认 FQN（`Blocks` → `-32602`）。skill 说清了，帮助没改。
7. **G7 RPC 方法名/参数 schema 的可发现性**：没有"列出全部方法"的命令；`snapshot.take`（任务书用的名字）实为 `snapshot.capture`，`craft.craft` 的 grid 槽是对象不是字符串——这些只有猜错撞 -32601/-32603 才知道。raw 的帮助说"check the equivalent subcommand's --help for the schema"，但子命令帮助只给 CLI 语法，不给 raw JSON 形状。
8. **G8 平面隔离的报错层级与文档不符**：对服务端实例调 gui.*，得到的是 CLI 本地 exit 1（"cannot discover mcdebug client socket…"或"expected client plane, got server"），永远到不了 RPC 层的 -32601。行为合理甚至更强，但帮助/错误码表没有描述这一层拦截。
9. **小问题**：(a) `-c` 不加 `--batch` 同样"失败即停、退出码=失败命令的码"（实测 `[2/3] ✗ … (stopping batch)`, exit 3），帮助只在 `--batch` 下写这个语义；(b) `storage get` 空槽 `capacity:1`（有货槽 64），易误读；(c) `status --health` 输出是人类可读文本，与其他命令的 JSON 风格不一致；(d) `entity.get`/`entity.attack` 不存在（读=entity.getNbt，攻击=world attack-entity），无方法清单可查（同 G7）。
